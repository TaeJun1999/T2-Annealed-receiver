# 01 — 작업 규칙

> **전제: 사용자는 오랫동안 접속하지 않는다(며칠일 수 있다).** 질문을 남기고 멈추면 그 시간이 통째로 날아간다. 그래서 이 문서는 "막혔을 때 무엇을 기본값으로 삼고 계속 갈지"를 미리 정해 둔 것이다.
>
> **시간 제한은 없다.** 오래 걸려도 된다. 대신 `00_GOAL.md` §3의 **게이트**를 건너뛰지 않는다. 빨리 끝내려고 검증을 생략하는 것이 이 작업에서 가장 큰 손실이다.

---

## 1. 제1원칙 — 멈추지 말고 기본값으로 계속한다

모호한 지점을 만나면:

1. `01_RULES.md` §4의 fallback 표에 답이 있는지 본다 → 있으면 그대로 적용.
2. 없으면 **가장 보수적인(= 우리 주장에 불리한) 선택**을 한다.
3. `conf/DECISIONS.md`에 한 줄 남긴다: `[시각] 무엇이 모호했나 | 무엇을 선택했나 | 왜 | 되돌리는 법`.
4. 계속 진행한다.

**질문을 던지고 대기하는 것은 §3의 hard stop 3종에서만 허용된다.**

## 2. 절대 금지

- `conf/` 밖에 쓰기 (예외: 종료 시 `docs/EXPERIMENTS.md`에 한 행 추가).
- `Demo/t2_route_a.py`, `Demo/t2_trellis.py`, `Demo/t2_gmm.py` 수정 — 회귀 테스트 t0/t6이 의존한다. 필요하면 `conf/code/`에 래퍼를 만든다.
- `docs/logs/`, `docs/plans/` 수정.
- 기존 `Demo/exp_*` 결과·raw 파일 삭제·덮어쓰기.
- 논문 알고리즘을 기억으로 재구성하기. `02_SPEC_baselines.md`에 옮겨 놓은 식만 쓴다. 그 식에 없는 것이 필요하면 fallback §4를 따르고 DECISIONS에 적는다.
- 결과가 나쁘다고 설정을 바꿔 재실행하기 (§5).

## 3. Hard stop — 이 3가지에서만 멈추고 사용자를 기다린다

1. `Demo/`의 파일을 수정해야만 진행 가능한 경우.
2. 서버 자원이 없어 실행 자체가 불가능한 경우(디스크 풀, 환경 파손).
3. 지침끼리 직접 모순되고 fallback도 없는 경우.

멈출 때는 `conf/BLOCKERS.md`에 상황·시도한 것·필요한 결정을 적고 **commit & push한 뒤** 종료한다. 그 시점까지의 모든 산출물도 함께 push한다.

그 외 모든 실패(테스트 FAIL, 발산, 수렴 안 함, 시간 초과)는 **멈출 이유가 아니다.** §6의 실패 처리 절차를 따른다.

## 4. Fallback 표 — 모호하면 여기를 본다

| 상황 | 기본값 |
|---|---|
| `Demo/`의 함수 이름·시그니처가 지침과 다름 | **repo가 정본.** repo에 맞춘다. 지침의 이름은 참고용 |
| LLR→soft symbol 변환 헬퍼를 못 찾겠음 | `t2_route_a.py`·`t2_trellis.py`를 끝까지 읽고 찾는다. 그래도 없으면 **직접 만들되 `07_SPEC_tests.md`의 S6(왕복 항등) 테스트로 잠근다** |
| SNR 격자를 모르겠음 | `Demo/exp_0925_run.py`의 격자를 읽어 그대로 쓴다. 읽을 수 없으면: 4×4 $T_p{=}2$ → 6/9/12/15 dB, $T_p{=}4$ → 0/3/6/9 dB. 8×4는 exp_0925 격자 우선, 없으면 4×4와 동일 격자 + 3 dB 시프트를 쓰고 DECISIONS에 기록 |
| prior 생성기(U/S/P) 사용법 | `Demo/t2_gmm.py`의 생성기를 그대로 쓴다. **prior S, 파일럿 = eigen-aligned**가 기본 |
| BiG-AMP damping $\beta$ | 0.7 (우리 관례). 발산하면 0.5 → 0.3 순으로 낮추고 **쓴 값을 결과 표에 기록** |
| BiG-AMP 내부 반복 $T_{\rm in}$ | 5 |
| BiG-AMP 채널 prior | i.i.d. $\mathcal{CN}(0, 1/N_r)$ (구조적 한계, 02번 문서 §2.3 참조) |
| R4 외부 반복 수 | **16** (전 arm 공통). 원문 20회 변형은 테스트 출력에만 병기 |
| $\alpha$ clip 범위 | $[\epsilon, 1-\epsilon]$, $\epsilon=10^{-6}$ (원문 명시) |
| 분산 하한 | $10^{-12}$ |
| 수치 발산 / NaN | 해당 블록을 `diverged`로 **분류해 기록**하고 마지막 유효 반복 결과를 반환. **NaN을 0으로 조용히 바꾸지 않는다** |
| arm 하나가 끝내 안 돌아감 | 그 arm을 `BLOCKED`로 표시하고 **나머지 arm으로 계속 진행** |
| 무언가를 버려야 함 | `00_GOAL.md` §5 우선순위 아래에서부터. $n$은 **어느 경우에도** 640 미만으로 낮추지 않는다 |
| score 학습이 발산·정체 | 그 시도를 FAIL로 `LADDER.md`에 기록 → 같은 칸 재시도(최대 3회) → 다음 칸. **게이트를 낮추지 않는다** |
| 사다리 전 칸 소진 | 학습 score arm 없이 나머지를 완주하고 그 사실을 결과로 보고 |
| D2 검증 T2d 실패 | **Stage B 중단.** BLOCKED로 올리고 사용자 판단 대기(검증 안 된 testbed의 숫자는 못 쓴다) |
| 학습 도중 중단·재시작 | 체크포인트에서 재개. 처음부터 다시 돌리지 않는다 |
| 병렬 실행 코어 수 | 지정하지 않는다(기본 = 전체 코어). 서버는 192코어, 사실상 단독 사용 |
| GPU를 쓸지 말지 | **기본은 CPU.** §9의 조건을 만족할 때만 GPU. 애매하면 CPU |
| GPU에서 OOM | 배치 크기를 절반씩 낮춘다 → 3회 시도 후에도 실패하면 **CPU로 폴백**하고 DECISIONS에 기록 |
| GPU가 없거나 점유 중 | **수신기 실행**은 CPU로 진행한다(기다리지 않는다). **학습은 CPU로라도 반드시 수행한다** — 64 실수 차원 MLP라 CPU에서도 가능하다. STATUS에 "GPU 없음, CPU 학습" 경고를 적고 epoch 예산을 유지한다. **학습을 건너뛰지 않는다** |
| 학습이 느려 보임 | 배치·모델 폭을 조정한다. **칸을 건너뛰지 않는다** |
| 랜덤 시드 | 기존 관례 `20260921 + 100 + SNR` 형식을 따르되 실험 번호만 바꾼다. **반드시 고정하고 결과 파일에 기록** |

## 5. 무결성 가드 — 이건 규칙이 아니라 연구 윤리다

이 프로젝트의 사용자 지침: *"연구를 완성하기 위해 억지로 조작하지 말 것."*

- **이번 실행의 BLER을 보고 arm·파라미터·격자를 고르지 않는다.** 설정은 실행 전에 확정하고, 실행 후에는 바꾸지 않는다.
- **사다리의 심판은 BLER이 아니라 사전 등록 품질 게이트다**(`04_SPEC_diffusion.md` §5). "게이트 미달이라 다음 모델로" = 정당. **"BLER이 나빠서 다른 모델로" = 금지.** 이 구분이 사다리 전체의 정당성이다.
- **모든 시도를 `conf/LADDER.md`에 남긴다.** 실패한 시도를 지우면 "고르지 않았다"를 보일 수 없게 된다.
- **"시도했다"의 정의:** 학습이 (i) 검증 loss 20 epoch 무개선으로 조기 종료했거나 (ii) 최소 200 epoch에 도달한 경우에만 그 칸을 시도한 것으로 친다. 그 전에 그만둔 것은 시도가 아니고, `LADDER.md`에 `ABORTED`로 적되 칸을 소진한 것으로 세지 않는다. **학습을 대충 돌리고 "게이트 미달"로 넘어가는 것은 사다리 전체를 무효로 만든다.**
- **diffusion에 GMM보다 많은 데이터·예산을 주지 않는다**(동일 $N_{\rm train}=10^4$, 동일 분할).
- **GMM arm을 약화시키지 않는다.** D2에서도 $K$ 전 범위 적합 + shrinkage + 검증 우도 early stopping을 그대로 적용한다(`05_SPEC_testbed_D2.md` §4).
- **testbed 선택 근거는 "물리적으로 표준이라서"이지 "GMM에 불리해서"가 아니다.** 후자를 문서·코드 주석·결과 파일 어디에도 쓰지 않는다.

  > **정정 (2026-09-23, review_next M-5.2a)** (사용자 위임에 따라 적용, 2026-09-22 CDT): 이 행의 금지("GMM에 불리해서" 를 쓰지 않는다)는 그대로다. 문제는 앞 절의 근거 "물리적으로 표준이라서" 다. 같은 기록의 두 곳이 반대로 적는다. `05_SPEC_testbed_D2.md:25` 는 "D2의 차별점은 "실제 채널"이 아니라 "조건부 Gaussian의 파괴"" 라 적는다. `results/NUMBERS_PACKAGE_2026-09-22.md:695` 는 철회 56 으로 "D2 is a standard mmWave channel, so the result transfers to real deployments." 를 인용 금지로 둔다. D2 의 정의(고정 |α_ℓ|, 연속 균등 각도, 고정 지수 PDP τ=2 — `05_SPEC_testbed_D2.md:16-18`)는 통제된 모델 하나이지 표준 채널이 아니다.
  > 제안 문구: "**testbed 선택 근거는 "조건부 Gaussian 가정의 파괴를 분리해 보는 통제 모델이라서"이지 "GMM에 불리해서"가 아니다.** 후자를 문서·코드 주석·결과 파일 어디에도 쓰지 않는다."
  > 같은 근거 문구가 `05_SPEC_testbed_D2.md:5`, `10_SPEC_stageC.md:176`, `PROMPT.md:88` 에도 있다(각각 노트 제안). `DECISIONS.md:23`([2026-09-20 12:35 KST] 행)의 근거 "D2 선택 근거가 "물리적으로 표준"이므로" 도 같은 문구이며, append-only 라 M-5.2a 정정 행이 대신 짚는다.

- 결과가 기대와 다르게 나와도 **재실행하지 않는다.** 한 번의 사전 등록 실행이다. 재실행이 필요해 보이면 그 이유를 DECISIONS에 적고 사용자 판단으로 남긴다.
- 실패한 블록, 발산한 arm, 수렴 안 한 케이스를 **표에서 빼지 않는다.** 그대로 남기고 개수를 센다.
- baseline을 불리하게 만들지 않는다: **전 arm 동일한 반복 수(16), 동일한 파일럿 행렬, 동일한 시드, 동일한 채널·잡음 실현**(셀 안에서 paired).
- 학습·적합 비용(GMM EM 시간 등)을 숨기지 않는다. 결과 표에 별도 열로 남긴다.
- "우리 모델"을 이번 결과로 고르지 않는다(`00_GOAL.md` §6).

## 6. 실패 처리 절차

1. 증상을 기록한다(무엇이, 어느 입력에서, 어떤 값으로).
2. **원인을 하나 특정한다.** 추측으로 여러 곳을 동시에 고치지 않는다.
3. 하나 고치고 재시험.
4. 3회 시도 후에도 실패하면: 그 항목을 `BLOCKED`로 표시, `conf/BLOCKERS.md`에 기록, **다음 작업으로 넘어간다.**

단위 테스트가 FAIL인 arm은 **본 실행에 넣지 않는다.** 검증 안 된 숫자를 결과 표에 남기지 않는다. 그 arm의 자리는 표에 `FAILED-VERIFICATION`으로 남긴다.

## 7. 보고 규약 (사용자의 유일한 창)

- 실행은 **반드시 tmux 안에서.** 세션이 끊겨도 살아남아야 한다.
- 모든 stdout/stderr는 `conf/logs/`에 tee. stderr는 별도 파일로.
- `conf/STATUS.md`를 **매 phase 종료 시 + 최소 30분마다** 갱신하고 **commit & push.** push하지 않으면 사용자는 아무것도 볼 수 없다.
- 커밋 메시지 형식: `conf: <phase> <한 줄 요약>`
- 중간 산출물도 push한다. 마지막에 몰아서 push하지 않는다. 5시간 뒤에 사용자가 보는 것이 "아무것도 없음"이면 안 된다.

### `conf/STATUS.md` 필수 항목

```
갱신 시각 / 경과 시간
현재 phase (P0~P7) 와 진척
완료한 것 (한 줄씩)
지금 하는 것
남은 것 + 예상 시간
BLOCKED 항목 (있으면)
DECISIONS 누적 건수
마지막 커밋 해시
```

## 8. 작업 순서

`00_GOAL.md` §3의 **Stage A(A0→A6) → Stage B(B1→B4)**. 앞 단계의 **종료 조건(게이트)** 을 만족하지 않고 다음으로 넘어가지 않는다. 단 §6에 따라 BLOCKED 처리된 항목은 예외로 두고 진행한다.

시간 제한이 없으므로 "시간이 없어서 게이트를 건너뛴다"는 선택지는 존재하지 않는다.

**P0에서 반드시 먼저 할 것:** `Demo/t2_route_a.py`, `Demo/t2_trellis.py`, `Demo/t2_gmm.py`, `Demo/exp_0925_run.py`, `Demo/exp_0925_analysis.py`, `CLAUDE.md`을 읽는다. 이 지침의 이름·시그니처는 전부 **참고용**이고, 충돌하면 repo가 이긴다.

## 9. 계산 자원 — CPU 기본, GPU는 조건부

서버는 192코어 CPU(사실상 단독 사용)와 GPU를 갖고 있다. 기존 실험(`exp_0925`: 51점 × $n{=}640$, 19분)은 **CPU 멀티프로세스**로 충분했다.

### 9.1 원칙

- **기본은 CPU 멀티프로세스.** 기존 러너 구조를 그대로 쓴다. `--jobs`는 지정하지 않는다.
- **GPU는 "측정된 병목"에만 쓴다.** 먼저 CPU로 돌려 시간을 재고, 그 phase가 `00_GOAL.md` §4 예산을 넘길 때만 GPU를 검토한다. 추측으로 미리 GPU 포팅하지 않는다 — 5시간 예산에서 가장 비싼 실수다.
- 시작 전에 `nvidia-smi`로 가용 GPU와 메모리를 확인하고 STATUS.md에 적는다. GPU가 없거나 다른 작업이 점유 중이면 **기다리지 말고 CPU로 진행한다.**

### 9.2 GPU가 실제로 도움이 되는 지점 (우선순위)

| 순위 | 대상 | 이유 |
|---|---|---|
| 1 | **GMM 적합(EM)**, $N_{\rm train}=10^4$, full covariance, 8×4 | 큰 배치 선형대수. 기존 CPU 실측 3분 25초 |
| 2 | **1024성분 batched mixture EP site / denoise** (`GMMPriorB`) | 성분 방향 배치가 크다 |
| 3 | **BiG-AMP을 블록 방향으로 배치** (Monte-Carlo 시행 $n$개를 한 텐서로) | 행렬 자체는 작지만($8\times4$) 시행이 많다 |

**GPU로 옮기지 말 것:** BCJR 트렐리스(`t2_trellis.py`). 시간 방향으로 순차적이고, `Demo/`는 수정 금지이며, 재구현은 정확성 위험이 이득보다 크다.

### 9.3 GPU를 쓸 때의 필수 조건 — 하나라도 어기면 결과가 무효다

1. **`Demo/`를 고치지 않는다.** GPU 경로는 `conf/code/`의 별도 래퍼로만 만든다.
2. **정밀도는 전 arm 동일.** 기본 `complex128`/`float64`. GPU에서 `complex128`이 느려 이득이 없으면 **GPU를 쓰지 않는다.** `complex64`로 내리려면 §9.4의 G1·G2를 통과해야 하고, 결과 파일 헤더에 정밀도를 적어야 한다.
3. **전 arm이 같은 경로를 쓴다.** 한 arm만 GPU로 돌려 수치가 달라지면 paired 비교(표 B)가 무효가 된다. 일부만 GPU로 돌릴 수 없으면 전부 CPU로 간다.
4. **결정론 고정.** 시드 고정, `torch.use_deterministic_algorithms(True)`, 비결정적 커널 금지. 테스트 C2(두 번 실행 비트 동일)가 GPU 경로에서도 통과해야 한다.
5. **결과 파일 헤더와 `docs/EXPERIMENTS.md` 행에 GPU 사용 여부·모델·정밀도를 기록한다.** 숨기지 않는다.

### 9.4 GPU 동등성 테스트 (GPU를 쓸 때만, `07_SPEC_tests.md` G1·G2)

- **G1** — 같은 시드에서 GPU 경로와 CPU 경로의 출력이 일치. `complex128`이면 $\le10^{-10}$, `complex64`면 $\le10^{-5}$ **이고 동시에** 블록별 성공/실패 판정이 100% 일치해야 한다.
- **G2** — G1의 판정 일치가 깨지면 **GPU 경로를 폐기하고 CPU로 돌아간다.** 속도를 위해 판정을 바꾸지 않는다.

### 9.5 score model 학습은 예외 — GPU를 먼저 쓴다

§9.1의 "CPU 기본"은 **수신기 실행**에 대한 규칙이다. **score model 학습(A5, B3)은 처음부터 GPU를 쓴다** — 여기서는 GPU가 명백한 정답이고, 측정해 볼 필요가 없다.

- 학습은 `float32`/`complex64`로 해도 된다(학습은 arm 간 paired 비교 대상이 아니다).
- 다만 **학습된 score를 수신기 안에서 평가할 때는 §9.2~9.4의 규칙이 그대로 적용된다.** 추론 정밀도는 전 arm 동일해야 하고, G1·G2를 통과해야 한다.
- 체크포인트는 `conf/ckpt/`에 저장하고 **git에 커밋하지 않는다**(경로와 크기만 STATUS에 기록).

### 9.6 자원이 부족할 때의 순서

① `00_GOAL.md` §5 우선순위의 아래 항목을 버린다 → ② 셀을 줄인다 → ③ GPU 배치를 줄인다. **$n$을 640 미만으로 낮추는 것은 어느 경우에도 하지 않는다.**
